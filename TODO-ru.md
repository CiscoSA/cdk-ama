## 1. Безопасность

### 1.1 Безопасность контейнеров и задач

- [ ] **Использовать read-only корневую файловую систему для контейнеров**
  - Контейнер в `ecs-cdk-stack.ts` (строки 96-119) не устанавливает `readonlyRootFilesystem: true`.
  - Добавьте `readonlyRootFilesystem: true` в определение контейнера и смонтируйте временный том для каталогов, требующих записи.

- [ ] **Запускать контейнеры от непривилегированного пользователя**
  - ✅ Уже сделано — `Dockerfile` строка 19: `USER node`.
  - CDK-стек не переопределяет это, поэтому проверка пройдена.

- [ ] **Использовать distroless или scratch образы**
  - ⚠️ Текущий Dockerfile использует `node:20-alpine` (минимальный, но не distroless).
  - Рассмотрите миграцию на `gcr.io/distroless/nodejs` или multi-stage сборку, копирующую только рантайм.

- [ ] **Удалить неиспользуемые Linux capabilities**
  - Контейнеры Fargate по умолчанию работают с ограниченными возможностями. Действий не требуется, но проверьте, что `linuxParameters` не добавляют лишних прав.

- [ ] **Сканировать зависимости приложения на уязвимости**
  - ✅ ECR `imageScanOnPush: true` установлен (строка 77).
  - ❌ В проекте не настроен CI/CD пайплайн или автоматическое сканирование зависимостей приложения (`npm audit`, Snyk и т.д.).

### 1.2 Сетевая безопасность

- [ ] **НЕ назначать публичные IP-адреса задачам Fargate в production**
  - ⚠️ `assignPublicIp: true` установлен на строке 144 в `ecs-cdk-stack.ts`.
  - Для production/staging используйте приватные подсети с NAT Gateway (уже настроен) и установите `assignPublicIp: false`.
  - Рассмотрите возможность настройки по окружениям (dev может использовать публичные IP для отладки).

- [ ] **Использовать сетевой режим `awsvpc` с группами безопасности**
  - ✅ Fargate использует `awsvpc` по умолчанию — без overlay-сети.
  - ⚠️ Паттерн `ApplicationLoadBalancedFargateService` создаёт группы безопасности по умолчанию, но они не кастомизированы.
  - Проверьте и ужесточите правила входящего/исходящего трафика (например, ограничьте входящий трафик только группой безопасности ALB).

- [ ] **Включить VPC Flow Logs**
  - ❌ Не настроено. Добавьте `flowLogs` в определение VPC (строки 69-72).
  - Требуется для аудита сетевого трафика и устранения неполадок.

- [ ] **Настроить AWS WAF для Application Load Balancer**
  - ❌ WAF не подключён к ALB.
  - Рассмотрите добавление AWS WAF для защиты от распространённых веб-атак (SQL-инъекции, XSS и т.д.).

- [ ] **Шифровать трафик сквозным образом (end-to-end)**
  - ✅ ALB поддерживает HTTPS при передаче `certificateArn`.
  - ✅ Трафик между ALB и задачами может быть незашифрован внутри VPC (допустимо для трафика в приватных подсетях).
  - ⚠️ Рассмотрите mutual TLS (mTLS) или сквозное шифрование для рабочих нагрузок, требующих соответствия нормативным требованиям.

### 1.3 Секреты и IAM

- [ ] **Использовать IAM-роли с минимальными привилегиями**
  - ✅ CDK автоматически генерирует роль выполнения задач и роль задачи с минимальными разрешениями — без ручных IAM-политик.
  - ✅ `Secrets Manager` используется для чувствительных данных (строки 59-67, 104-111).
  - ⚠️ Роль задачи, создаваемая паттерном по умолчанию, может иметь больше разрешений, чем необходимо — проверьте и ограничьте.

- [ ] **Шифровать образы ECR с помощью управляемого клиентом ключа KMS**
  - ✅ Шифрование по умолчанию включено (ключ, управляемый AWS).
  - ⚠️ Рассмотрите использование управляемого клиентом ключа KMS для соответствия нормативным требованиям.

## 4. Инфраструктура как код (CDK) — Best Practices

### 4.1 Организация кода

- [ ] **Разделить stateful и stateless ресурсы в разные стеки**
  - ❌ Репозиторий ECR (stateful) и сервис ECS (stateless) находятся в одном стеке.
  - Рассмотрите разделение на `EcrStack` (stateful, с `RemovalPolicy.RETAIN`) и `EcsStack` (stateless).

- [ ] **Использовать сгенерированные имена, а не физические**
  - ⚠️ Репозиторий ECR имеет физическое имя `ecs-app-${envName}` (строка 75). Это предотвращает развёртывание нескольких стеков с тем же именем окружения в одном аккаунте.
  - ⚠️ Секрет Secrets Manager имеет физическое имя `${envName}/app-secrets` (строка 60).
  - Рассмотрите возможность автоматической генерации имён CDK или использования уникальных суффиксов.

- [ ] **Зафиксировать `cdk.context.json` в системе контроля версий**
  - ❌ Файл отсутствует в списке файлов проекта. Если выполнялись поиски VPC или зон доступности, файл контекста должен быть закоммичен.

### 4.2 Тестирование

- [ ] **Написать инфраструктурные тесты**
  - ❌ Тесты в `ecs-cdk.test.ts` полностью закомментированы.
  - Добавьте тесты с использованием `aws-cdk-lib/assertions` для проверки:

    - Группы безопасности настроены корректно
    - IAM-роли следуют принципу минимальных привилегий
    - Используются корректные комбинации CPU/памяти
    - Logical ID stateful-ресурсов остаются стабильными

### 4.3 Проверка соответствия требованиям (Compliance)
